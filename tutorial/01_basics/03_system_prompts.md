# 03 — System prompts і multi-turn діалог

## Що таке system prompt

System prompt — окреме поле в запиті (не в масиві `messages`), яке задає **контекст і поведінку** моделі для всієї розмови. Він обробляється перед user-повідомленнями і має найвищий пріоритет інструкцій.

```ts
{
  system: "You are a grumpy senior developer.",  // окреме поле
  messages: [
    { role: "user", content: "How do I exit vim?" }
  ]
}
```

Якщо system prompt суперечить user-повідомленню — модель, як правило, дотримується system prompt.

---

## API є повністю stateless

Це **найважливіша концепція** для розуміння того як працюють LLM-додатки.

Сервер Anthropic **не зберігає нічого між запитами**. Кожен `messages.create()` — незалежний HTTP запит. Якщо ти хочеш щоб модель пам'ятала попередні повідомлення — ти сам ведеш масив і відправляєш всю історію кожного разу:

```
Запит 1: messages = [{ role: "user", content: "My name is Alex." }]
Запит 2: messages = [
  { role: "user",      content: "My name is Alex." },
  { role: "assistant", content: "Hi Alex!" },
  { role: "user",      content: "What's my name?" }   // ← нове
]
```

Весь масив цілком летить на сервер щоразу.

---

## Чому це важливо

1. **Токени = гроші.** Чим довша історія — тим дорожче кожен наступний запит.
2. **Context window.** Вся історія + відповідь мусять вміститись у 200k токенів.
3. **Стратегія стиснення.** В реальних продуктах старі повідомлення або обрізають, або стискають через окремий запит до моделі ("summarize the conversation so far").

---

## Правила для масиву messages

- Повідомлення мають строго чергуватись: `user → assistant → user → assistant ...`
- Перше повідомлення завжди `user`
- Не можна два `user` повідомлення підряд — буде помилка від API

---

## Підводні камені

**1. System prompt vs user instruction — різна "вага".**
Якщо і в system і в user є суперечливі інструкції, модель зазвичай надає перевагу system. Але це не гарантія — можна "переконати" через user при певних формулюваннях.

**2. Stateless ≠ дешево.**
Новачки думають що "нова розмова дешевша". Ні — ти все одно відправляєш всю ту ж саму систем-промпт і контекст. Оптимізація йде через **prompt caching** (тема 03_advanced).

**3. Роль assistant в history — твоя відповідальність.**
Коли ти будуєш history вручну і додаєш `{ role: "assistant", content: "..." }` — ти можеш туди написати що завгодно, навіть те що модель ніколи не казала. Це і фіча (few-shot examples), і потенційна дірка в безпеці.
