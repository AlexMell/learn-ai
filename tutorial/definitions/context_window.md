# Context Window

## Поясни 7-річному

Уяви, що модель — це людина, яка читає текст через маленьке віконечко. Вона бачить лише те, що потрапляє у вікно прямо зараз. Що не влізло — не існує. Чим більше вікно — тим більше вона може тримати в голові одночасно. Але навіть з великим вікном — те, що посередині, вона бачить гірше, ніж початок і кінець.

---

## Що таке Context Window

**Context Window** — максимальна кількість токенів, яку модель обробляє за один запит. Включає **все**: system prompt + history + поточний user message + відповідь моделі.

```
┌─────────────────────────────────────────────┐
│  System prompt  │  History  │  User  │  Out │
│   (input)       │  (input)  │ (input)│ (put)│
└─────────────────────────────────────────────┘
        ←────────── Context Window ──────────→
```

Якщо сума токенів перевищує ліміт — API поверне помилку `400`.

### Розміри у Claude (2025)

| Модель | Context Window | Max Output |
|---|---|---|
| claude-haiku-4-5 | 200,000 | 8,192 |
| claude-sonnet-4-6 | 200,000 | 64,000 |
| claude-opus-4-8 | 200,000 | 32,000 |

200k токенів ≈ 150,000 слів ≈ ~500 сторінок A4 ≈ невеликий роман.

### Важливо: output "з'їдає" вікно

`max_tokens` — це ліміт на output, але він резервується з загального контексту. Якщо context window = 200k і input = 190k токенів — для output залишилось лише 10k, навіть якщо `max_tokens: 64000`.

## "Lost in the Middle" проблема

### Що це

Дослідження (Liu et al., 2023) показало: моделі значно гірше використовують інформацію, що знаходиться **в середині** довгого контексту, порівняно з початком і кінцем.

```
Якість витягування інформації залежно від позиції:

Початок  ████████████ висока
Середина ████         низька   ← проблема
Кінець   ██████████   висока
```

### Чому так відбувається

Attention механізм краще "тримає" позиції ближче до поточного токену (кінець) і до спеціальних позицій на початку (system prompt, перші повідомлення). Середина "розмивається" при великих контекстах.

### Практичний наслідок

```
❌ Неправильно:
[System prompt] [500 сторінок документа] [Питання]
                     ↑
               ключовий факт на сторінці 250 — модель може його пропустити

✓ Правильно:
[System prompt] [Питання] [500 сторінок документа]
або
[System prompt] [Документ] [Питання повторено наприкінці]
```

**Правило**: важливі інструкції — на початку (system prompt) і в кінці (user message). Не покладайся на те, що модель знайде щось посередині великого документа.

## Як працювати з обмеженнями

### Стратегія 1: Chunking (розбивка на частини)

Розбити великий документ на частини і обробляти послідовно або паралельно.

```ts
const CHUNK_SIZE = 10_000; // токенів на чанк

function chunkText(text: string, size: number): string[] {
  const words = text.split(' ');
  const chunks: string[] = [];
  let current: string[] = [];
  let tokenCount = 0;

  for (const word of words) {
    const wordTokens = Math.ceil(word.length / 4); // груба оцінка
    if (tokenCount + wordTokens > size) {
      chunks.push(current.join(' '));
      current = [word];
      tokenCount = wordTokens;
    } else {
      current.push(word);
      tokenCount += wordTokens;
    }
  }
  if (current.length) chunks.push(current.join(' '));
  return chunks;
}
```

**Мінус**: модель не бачить зв'язків між чанками.

---

### Стратегія 2: RAG (Retrieval-Augmented Generation)

Замість того щоб давати весь документ — витягуй лише релевантні фрагменти.

```
Великий документ
      ↓
Розбити на чанки → Embeddings (векторизація)
      ↓
User query → знайти найближчі чанки (vector search)
      ↓
Підсунути лише релевантні ~3-5 чанки в контекст
      ↓
Claude відповідає на основі точних фрагментів
```

**Плюс**: модель бачить тільки потрібне, галюцинацій менше, дешевше.
**Мінус**: якість залежить від якості retrieval — якщо не те знайшли, не те й відповідь.

---

### Стратегія 3: Summarization Chain

Ітеративне стиснення довгого тексту.

```
Документ розбити на чанки
      ↓
Summarize chunk 1 → summary_1 (500 токенів)
Summarize chunk 2 → summary_2 (500 токенів)
...
      ↓
Combine summaries → final_summary
      ↓
Відповідати на питання на основі final_summary
```

**Мінус**: деталі губляться на кожному кроці стиснення.

---

### Стратегія 4: Map-Reduce

Паралельна обробка чанків + агрегація результатів.

```
Документ
  ├── chunk_1 → [відповідь 1]  ┐
  ├── chunk_2 → [відповідь 2]  ├── Reduce → фінальна відповідь
  └── chunk_3 → [відповідь 3]  ┘
```

Корисно для: підрахунку, класифікації, пошуку конкретних фактів по великому тексту.

---

### Стратегія 5: Sliding Window

Якщо важливий порядок і зв'язок між частинами — рухати вікно з перекриттям.

```
[chunk_1        ]
         [chunk_2        ]
                  [chunk_3        ]
         ← overlap →
```

Overlap зберігає контекст між чанками. Дорожче (токени дублюються), але зберігає зв'язність.

## Самоперевірка: "Що робити з документом на 200к токенів?"

**Питання**: є PDF на 400 сторінок (~200k токенів). Треба відповідати на питання по ньому. Як?

### Варіант A: "Засунути все в контекст"

```
✓ Працює технічно (200k вміщується)
✗ Дорого: кожен запит = 200k input токенів
✗ "Lost in the middle" — відповіді на питання про середину документа будуть гіршими
✗ Повільно: processing 200k токенів на кожен запит
```

**Коли підходить**: одноразовий запит, документ реально потрібен цілий, бюджет не критичний.

### Варіант B: RAG (рекомендований для продакшену)

```
✓ Дешево: в контексті лише 2-5k токенів релевантного тексту
✓ Швидко
✓ Масштабується на мільйони документів
✗ Потрібна інфраструктура: vector DB, embedding model
✗ Якість обмежена якістю retrieval
```

**Коли підходить**: повторювані запити, великі бази документів, продакшн-система.

### Варіант C: Summarization (якщо потрібен огляд)

```
✓ Отримуєш стислий огляд всього документа
✗ Деталі губляться
✗ Не підходить для точних питань ("яка сума в пункті 4.2.1?")
```

**Коли підходить**: "про що цей документ?", "які головні тези?", executive summary.

### Правильна відповідь на інтерв'ю

> "Залежить від задачі. Якщо потрібні точні відповіді на конкретні питання — RAG: розбиваємо на чанки, векторизуємо, витягуємо релевантні фрагменти. Якщо потрібен загальний огляд — summarization chain. Якщо це одноразовий аналіз і бюджет дозволяє — можна засунути все в контекст, але треба пам'ятати про 'lost in the middle' і розміщувати питання наприкінці."

## Підводні камені

### 1. Помилка виникає під час запиту, не під час підготовки
API не перевіряє довжину заздалегідь. Помилка `400` прийде лише коли надсилаєш запит. Завжди рахуй токени перед відправкою через `countTokens()`.

### 2. History у multi-turn діалозі росте
Кожен turn додає токени. Після 10-20 повідомлень контекст може переповнитись.

```ts
// Стратегії управління history:
// 1. Зберігати лише останні N повідомлень
// 2. Стискати старі повідомлення (summary)
// 3. Видаляти найменш важливі повідомлення
```

### 3. System prompt займає місце завжди
Якщо system prompt = 5k токенів, він витрачається на **кожен** запит. При 1M запитів = 5B зайвих токенів. Prompt caching вирішує це частково.

### 4. 200k ≠ "необмежено"
200k токенів — багато, але модель все одно може "забути" деталі з початку при дуже довгих контекстах. Ефективна увага не є рівномірною по всьому вікну.

## Interview Q&A

**Q: Що таке context window і що в нього входить?**
A: Максимальна кількість токенів за один запит. Включає все: system prompt, conversation history, поточне повідомлення і відповідь моделі. У Claude — 200k токенів. Якщо перевищити — API поверне помилку 400.

---

**Q: Що таке "lost in the middle" і як це враховувати?**
A: Моделі гірше використовують інформацію з середини довгого контексту. Attention краще "тримає" початок і кінець. Тому важливі інструкції — в system prompt або наприкінці user message. Критичний факт, похований на сторінці 250 великого документа, може бути проігнорований.

---

**Q: Як обробити документ більший за context window?**
A: Chunking + RAG для точних питань, summarization chain для огляду, map-reduce для паралельної обробки. Вибір залежить від задачі: RAG — для продакшену з повторюваними запитами, summarization — для одноразового огляду.

---

**Q: Чому history у multi-turn діалозі може стати проблемою?**
A: Кожне повідомлення додає токени до контексту. Після багатьох turns сума може перевищити context window. Треба або обрізати старі повідомлення, або стискати їх у summary, або явно керувати довжиною history.

---

**Q: Навіщо рахувати токени через `countTokens()` якщо є великий ліміт?**
A: Щоб уникнути помилки 400 під час реального запиту (що може бути дорогим або критичним). Також для оцінки вартості перед відправкою і для динамічного обрізання контенту (RAG, history) до безпечного розміру.

---

## Корисні числа напам'ять

```
200k tokens ≈ 150k слів ≈ 500 сторінок A4 ≈ невеликий роман

"Lost in the middle": середина контексту = найгірша якість attention
Важливе → на початок (system) або кінець (user message)

RAG chunk розмір: зазвичай 512–2048 токенів
Overlap між чанками: 10–20% від розміру чанку

History management: зберігати останні 10-20 повідомлень або стискати
```
