# Як LLM генерує відповідь

## Поясни 7-річному

Уяви, що ти граєш у гру: тобі дають початок речення — "Сьогодні погода..." — і ти маєш вгадати наступне слово. Ти думаєш: "мабуть `гарна` або `дощова`". Комп'ютер робить те саме — він дивиться на всі слова, що вже є, і вгадує найбільш підходяще наступне. Потім дивиться знову і знову вгадує. Слово за словом — так і будується відповідь.

---

## Next Token Prediction

LLM — це машина з однією задачею: **передбачити наступний токен**.

### Як це працює покроково

```
Input: "The capital of France is"
         ↓
Модель дивиться на всі токени одночасно (через attention)
         ↓
Для кожного можливого наступного токена рахує score (logit)
         ↓
Logits → Softmax → Probability distribution
         ↓
{"Paris": 0.87, "Lyon": 0.05, "a": 0.03, ...}
         ↓
Семплінг → "Paris"
         ↓
"Paris" додається до контексту, процес повторюється
```

Модель ніколи не "думає наперед" — вона завжди генерує лише **один токен за раз**, авторегресивно.

### Autoregressive generation

```
Step 1: "The capital of France is" → "Paris"
Step 2: "The capital of France is Paris" → "."
Step 3: "The capital of France is Paris." → [EOS]
```

Кожен новий токен додається до контексту і стає частиною вхідних даних для наступного кроку. Саме тому output токени дорожчі за input — кожен потребує окремого forward pass.

---

## Probability Distribution та Sampling

Після softmax модель має розподіл ймовірностей по всьому словнику (~100k токенів). Далі — **sampling**: як обрати токен з цього розподілу.

Три основних режими:

| Режим | Що робить |
|---|---|
| Greedy | Завжди обирає токен з найвищою ймовірністю |
| Temperature sampling | Змінює "гостроту" розподілу перед семплінгом |
| Top-p (nucleus) sampling | Обирає з найменшого набору токенів, що покривають p% ймовірності |

---

## Temperature

**Temperature** — параметр, що контролює "випадковість" або "впевненість" моделі.

### Математика (просто)

Перед softmax логіти діляться на temperature `T`:

```
logits_scaled = logits / T
probabilities = softmax(logits_scaled)
```

- `T < 1` → логіти збільшуються → розподіл стає гострішим → модель більш впевнена
- `T > 1` → логіти зменшуються → розподіл стає плоскішим → модель більш "творча"
- `T = 1` → без змін (дефолт)
- `T = 0` → еквівалент greedy decoding (завжди найймовірніший токен)

### Візуально

```
Temperature = 0.1 (низька):        Temperature = 1.5 (висока):
"Paris": ████████████ 95%          "Paris": ████ 40%
"Lyon":  █ 3%                      "Lyon":  ███ 25%
"Nice":  · 1%                      "Nice":  ██ 20%
"Rome":  · 1%                      "Rome":  ██ 15%
```

### Коли крутити

| Задача | Temperature | Чому |
|---|---|---|
| Факти, код, SQL, JSON | 0 – 0.3 | Потрібна точність, не варіативність |
| Чат, пояснення | 0.5 – 0.8 | Баланс зв'язності і природності |
| Копірайтинг, ідеї | 0.9 – 1.2 | Більше варіативності, менше "шаблонності" |
| Brainstorm, поезія | 1.2 – 1.5 | Несподівані комбінації |
| > 1.5 | не рекомендується | Текст стає некогерентним |

**Правило**: якщо відповідь має бути правильною — низька температура. Якщо цікавою — вища.

## Top-p (Nucleus Sampling)

**Top-p** — альтернативний спосіб контролювати семплінг.

### Ідея

Замість фіксованої кількості токенів (top-k) — беремо **мінімальний набір токенів**, сумарна ймовірність яких ≥ p.

```
p = 0.9

Sorted tokens:
"Paris": 0.60  ← сума: 0.60
"Lyon":  0.20  ← сума: 0.80
"Nice":  0.10  ← сума: 0.90 ✓ стоп
"Rome":  0.05  ← не включається
...

Семплінг лише з {"Paris", "Lyon", "Nice"}
```

### Temperature vs Top-p

- **Temperature** змінює форму всього розподілу.
- **Top-p** обрізає "хвіст" розподілу після семплінгу.

Вони діють разом: спочатку temperature трансформує logits, потім top-p обрізає хвіст.

### Коли використовувати top-p

- `top_p = 1.0` — без обрізання (дефолт)
- `top_p = 0.9` — легке обрізання випадкових малоймовірних токенів
- `top_p = 0.5` — тільки найімовірніші токени

**Загальна рекомендація**: міняй або temperature, або top-p — не обидва одночасно. Зазвичай достатньо temperature.

## Stop Sequences

**Stop sequences** — рядки, при генерації яких модель негайно зупиняється.

```ts
const response = await anthropic.messages.create({
  model: "claude-sonnet-4-6",
  max_tokens: 1024,
  stop_sequences: ["\n\nHuman:", "###", "<END>"],
  messages: [...]
});
```

### Як це працює

Модель генерує токени один за одним. Після кожного токена перевіряється: чи утворює поточний текст один зі stop sequences? Якщо так — генерація зупиняється, stop sequence **не включається** у відповідь.

### `stop_reason` у відповіді

```ts
message.stop_reason
// "end_turn"       — модель сама вирішила зупинитись
// "max_tokens"     — досягнуто ліміт токенів
// "stop_sequence"  — спрацював один зі stop sequences
```

```ts
message.stop_sequence
// "\n\nHuman:" — який саме рядок спрацював
```

### Типові use cases

| Stop sequence | Навіщо |
|---|---|
| `"\n\nHuman:"` | Зупинити симуляцію діалогу |
| `"###"` | Розділювач між секціями у structured output |
| `"</tool_call>"` | Зупинити після завершення виклику інструменту |
| `"\n"` | Отримати лише один рядок відповіді |
| `"0"`, `"1"` ... | Класифікація: очікуємо лише одну цифру |

### Підводний камінь

Stop sequence перевіряється на рівні тексту, але генерація токенова. Якщо `"\n\n"` є частиною більшого токену — перевірка відбувається після декодування. Зупинка гарантована, але може бути на токен пізніше ніж очікуєш.

## Чому LLM "галюцинує"

**Галюцинація** — коли модель генерує впевнений, правдоподібний, але фактично неправильний текст.

### Причина 1: Next token prediction не знає "правди"

Модель не зберігає факти — вона навчилась передбачати токени, що статистично слідують за попередніми. Якщо в тренувальних даних "автор книги X" часто йшов поряд з іменем Y — модель видасть Y, навіть якщо це неправда.

### Причина 2: Розподіл ймовірностей завжди щось генерує

Модель **зобов'язана** вибрати наступний токен. Немає варіанту "я не знаю" на рівні архітектури — лише розподіл і семплінг. Якщо вірного токена немає у словнику з високою ймовірністю — обирається найближчий неправильний.

### Причина 3: Confidence ≠ Correctness

Температура = 0 дає найімовірніший токен, але не найправильніший. Висока ймовірність означає "це статистично схоже на правильну відповідь", а не "це правда".

### Причина 4: Training data cutoff

Модель не знає подій після дати зрізу тренувальних даних. Але вона не каже "я не знаю" — вона продовжує генерувати на основі патернів.

### Причина 5: Attention розмивається на довгих контекстах

На дуже довгих вхідних текстах модель може "загубити" деталі з початку контексту і генерувати відповідь, що суперечить наданій інформації.

### Як боротись з галюцинаціями

| Техніка | Суть |
|---|---|
| RAG | Надавати перевірені факти в контексті |
| Low temperature | Зменшити варіативність на фактичних задачах |
| Structured output | Обмежити формат відповіді |
| Chain-of-thought | Змусити модель "думати" перед відповіддю |
| Verification step | Додатковий запит для перевірки відповіді |
| Explicit "I don't know" | У system prompt дозволити/вимагати відмову від відповіді |

## Interview Q&A

**Q: Як LLM генерує текст?**
A: Авторегресивно — один токен за раз. На кожному кроці модель дивиться на весь попередній контекст, рахує logits для кожного токена словника, застосовує softmax для отримання розподілу ймовірностей, і семплює наступний токен. Потім цей токен додається до контексту, і процес повторюється до stop_reason.

---

**Q: Що таке temperature і коли її зменшувати?**
A: Temperature ділить logits перед softmax. При T < 1 розподіл стає гострішим — модель впевненіша. При T > 1 — плоскішим, більше варіативності. Для коду, фактів, JSON — низька (0–0.3). Для творчих задач — висока (0.9–1.2).

---

**Q: Чим top-p відрізняється від temperature?**
A: Temperature трансформує весь розподіл ймовірностей. Top-p обрізає "хвіст" — залишає лише мінімальний набір токенів з сумарною ймовірністю ≥ p. Вони застосовуються разом, але змінювати обидва одночасно зазвичай не потрібно.

---

**Q: Чому LLM галюцинує?**
A: Тому що модель не зберігає факти — вона передбачає статистично правдоподібний наступний токен. Архітектурно немає варіанту "я не знаю" — є лише розподіл ймовірностей. Якщо правильна відповідь недостатньо представлена в тренувальних даних, модель впевнено генерує неправильну.

---

**Q: Що таке stop sequences і як вони впливають на генерацію?**
A: Рядки, при появі яких генерація негайно зупиняється. Після кожного токена Claude перевіряє: чи утворює поточний текст один зі stop sequences. Якщо так — `stop_reason` = `"stop_sequence"`, рядок не включається у відповідь. Корисно для structured output, симуляції діалогів, обмеження формату.

---

**Q: Що означає `stop_reason: "max_tokens"`?**
A: Модель не завершила думку — вона була примусово зупинена через досягнення ліміту `max_tokens`. Відповідь може бути обрізана посередині речення. Це сигнал збільшити `max_tokens` або скоротити input.

---

## Корисні числа напам'ять

```
Temperature:
  0       → greedy (завжди найімовірніший токен)
  0–0.3   → факти, код, JSON
  0.5–0.8 → чат, пояснення
  0.9–1.2 → творчість, копірайтинг
  > 1.5   → некогерентний текст

Top-p:
  1.0 → без обрізання (дефолт)
  0.9 → легке обрізання хвоста
  0.5 → тільки найімовірніші токени

stop_reason варіанти: "end_turn" | "max_tokens" | "stop_sequence"
```
