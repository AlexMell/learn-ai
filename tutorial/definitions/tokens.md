## Поясни токени 7-річному

Уяви, що ти складаєш пазл зі слів. Але замість цілих слів у тебе є шматочки — деякі великі (ціле слово), деякі маленькі (половинка слова або буква). Комп'ютер не вміє читати букви як ти — він вміє лише рахувати. Тому кожен шматочок отримує свій номер: `кіт` → `4521`, `при` → `892`, `віт` → `340`. Коли ти пишеш "Привіт" — комп'ютер бачить `[892, 340]`. Він думає числами, а не словами. Ці числові шматочки й називаються токенами.

---

## Що таке токен

Токен — це найменша одиниця тексту, з якою працює мовна модель. Модель ніколи не бачить символи або слова напряму — лише числові ID токенів.

Токен — не завжди слово. Це може бути:
- ціле слово: `hello` → 1 токен
- частина слова: `unbelievable` → `un` + `believ` + `able` → 3 токени
- знак пунктуації: `,` → 1 токен
- пробіл разом з наступним словом: ` the` → 1 токен
- цифра: `2024` → 1 або кілька токенів залежно від числа

Грубе правило для англійської: **1 токен ≈ 4 символи ≈ 0.75 слова**.

## Як працює токенайзер

### Алгоритм: Byte Pair Encoding (BPE)

BPE — найпоширеніший алгоритм токенізації в LLM (GPT, Claude, Llama).

**Ідея**: починаємо з окремих байтів/символів і ітеративно об'єднуємо найчастіші пари.

**Процес навчання токенайзера:**
1. Беремо великий корпус тексту.
2. Починаємо з алфавіту (усі унікальні символи/байти).
3. Знаходимо найчастішу пару символів → об'єднуємо в новий токен.
4. Повторюємо до досягнення потрібного розміру словника (наприклад, 100k токенів).

**Приклад:**
```
Корпус: "low lower lowest"
Початок: l, o, w, e, r, s, t (окремі символи)
Крок 1: "lo" зустрічається 3 рази → об'єднати → lo
Крок 2: "low" → об'єднати → low
Крок 3: "er" → об'єднати → er
Результат: low | er | low | est
```

### Словник токенів (Vocabulary)

Claude використовує словник ~100,000 токенів. Кожен токен має числовий ID:
```
"Hello" → 9906
" world" → 1917
"!" → 0
```

Модель оперує саме цими числами, не текстом.

### Що відбувається під час інференсу

```
Вхідний текст
    ↓
Токенайзер → список числових ID [9906, 1917, 0, ...]
    ↓
Модель обробляє послідовність ID
    ↓
Модель передбачає наступний ID (logits → softmax → sampling)
    ↓
Декодер → текст
```

## Чому українська (і інші не-англійські мови) дорожча

### Причина: нерівномірне покриття словника

Токенайзер навчався **переважно на англійському тексті**. Тому:

- Англійські слова добре представлені у словнику → мало токенів
- Слова інших мов "розбиваються" на дрібні шматки → багато токенів

**Конкретний приклад:**
```
"Hello" → 1 токен
"Привіт" → 3-4 токени (при-, ві-, т або П-ри-ві-т)

"I love programming" → ~4 токени
"Я люблю програмування" → ~8-10 токенів
```

### Коефіцієнти (приблизно)

| Мова | Токенів на слово | Відносна вартість |
|---|---|---|
| Англійська | ~1.3 | 1x |
| Французька/Іспанська | ~1.5 | ~1.2x |
| Українська/Російська | ~2.5-3.5 | ~2-3x |
| Японська/Китайська | ~1.5-2 | ~1.5x |
| Арабська | ~3-5 | ~3-4x |

### Технічна причина: UTF-8 fallback

Якщо слово/символ не знайшовся у словнику, токенайзер розбиває його на **UTF-8 байти**. Кириличний символ = 2 байти → 2 токени на один символ у найгіршому випадку.

Кирилиця в UTF-8: кожна буква = 2 байти → в найгіршому випадку кожна літера = окремий токен.

### Практичний висновок

Якщо пишеш system prompt українською — він може коштувати в 2-3 рази більше токенів, ніж аналогічний англійський. При великих обсягах запитів **system prompt краще писати англійською**.

## Context Window

**Context window** — максимальна кількість токенів, яку модель може "бачити" одночасно (input + output разом).

| Модель | Context Window |
|---|---|
| claude-haiku-4-5 | 200,000 токенів |
| claude-sonnet-4-6 | 200,000 токенів |
| claude-opus-4-8 | 200,000 токенів |

200k токенів ≈ 150,000 слів ≈ ~500 сторінок тексту.

**Важливо**: контекстне вікно включає і input, і output. Якщо відповідь довга — вона "з'їдає" місце для наступних запитів у multi-turn діалозі.

---

## Вхідні та вихідні токени: ціна різна

```
Input tokens:  дешевші (те, що ти надсилаєш)
Output tokens: дорожчі (~3-5x від input)
```

**Чому output дорожчий:**
- Генерація послідовна: кожен токен генерується по одному (autoregressive).
- Input можна обробити паралельно (attention over all tokens at once).
- Output потребує окремого forward pass на кожен токен.

**Приблизні ціни Claude Sonnet 4.6 (станом на 2025):**
- Input: $3 / 1M токенів
- Output: $15 / 1M токенів

## Підводні камені (Gotchas)

### 1. Токени ≠ слова → непередбачувані розбивки
```js
// "2024" може бути 1 токеном, а "2,024" — вже 3 токени
// Математичні формули розбиваються дуже погано
// URL-адреси = десятки токенів
```

### 2. Пробіл — частина токену
`"dog"` і `" dog"` — різні токени. Це впливає на промпт-інженерінг: пробіл перед словом міняє токенізацію.

### 3. Лічильник у API — завжди токени, не символи
Ліміти, ціна, `max_tokens` — все у токенах. Якщо ставиш `max_tokens: 100` для кирилиці — отримаєш набагато менше тексту, ніж для англійської.

### 4. Stop sequences перевіряються на рівні токенів
`stop_sequences: ["\n"]` — зупинка відбувається лише коли модель генерує токен, що містить `\n`. Якщо `\n` є всередині більшого токену — зупинки не буде.

### 5. Prompt caching — byte-identical
Для того щоб Claude закешував блок промпту, він має бути **байт-ідентичним** між запитами. Навіть зайвий пробіл — інший набір токенів → кеш не спрацює.

### 6. Off-by-one при streaming
При стрімінгу ти отримуєш токени по одному. `input_tokens` у `message_start` не включає поточний стрімінг-блок — він рахується окремо у `message_delta`.

### 7. Токени і семантика
Слово `"unhappy"` може бути токенізоване як `un` + `happy`. Модель це знає, але **це не означає**, що вона завжди правильно розуміє морфеми. Просто факт архітектури.

## countTokens() — як рахувати заздалегідь

```ts
const response = await anthropic.messages.countTokens({
  model: "claude-sonnet-4-6",
  system: "You are a helpful assistant.",
  messages: [{ role: "user", content: "Hello!" }],
});

console.log(response.input_tokens); // кількість токенів без реального запиту
```

**Навіщо**: перевірити чи не перевищуємо context window перед дорогим запитом, оцінити вартість.

**Важливо**: `countTokens` — окремий API-запит, теж коштує (але дешево).

## usage object у відповіді

```ts
const message = await anthropic.messages.create({ ... });

console.log(message.usage);
// {
//   input_tokens: 142,
//   output_tokens: 87,
//   cache_creation_input_tokens: 0,  // якщо використовується prompt caching
//   cache_read_input_tokens: 0,
// }
```

`cache_read_input_tokens` — кількість токенів, прочитаних з кешу (вартість ~10% від звичайного input).

## Interview Q&A

**Q: Що таке токен в контексті LLM?**
A: Найменша одиниця тексту, з якою працює модель. Це не символ і не слово, а підрядок, визначений алгоритмом BPE під час навчання токенайзера. Модель оперує числовими ID токенів, не символами.

---

**Q: Як працює BPE (Byte Pair Encoding)?**
A: Алгоритм починає з окремих байтів і ітеративно об'єднує найчастіші пари символів у нові токени. Це робиться на великому корпусі тексту до досягнення потрібного розміру словника. У результаті часті слова — цілі токени, рідкісні — розбиваються на частини.

---

**Q: Чому Ukrainian/Russian текст коштує більше токенів?**
A: Токенайзер навчений переважно на англійських даних. Кириличні слова рідше зустрічаються у словнику токенів → розбиваються на більше частин. Додатково: кирилиця в UTF-8 = 2 байти на символ, і при fallback на байтовий рівень кожна буква стає окремим токеном.

---

**Q: Яка різниця між input і output токенами з точки зору ціни і чому?**
A: Output токени дорожчі (~3-5x). Input обробляється паралельно через attention механізм. Output генерується авторегресивно — один токен за раз, кожен потребує окремого forward pass через усю модель.

---

**Q: Що таке context window?**
A: Максимальна кількість токенів (input + output разом), яку модель може обробити в одному запиті. Для Claude — 200k токенів. Якщо перевищити — або помилка, або модель "забуває" початок контексту (залежно від реалізації).

---

**Q: Як prompt caching пов'язаний з токенами?**
A: Кешований блок зберігається на стороні Anthropic між запитами. Читання з кешу коштує ~10% від звичайної ціни input токенів. Умова: текст блоку має бути byte-identical між запитами (і мінімум 1024 токени для кешування).

---

**Q: Чому `max_tokens: 100` дає різну кількість тексту для різних мов?**
A: Тому що токени різних мов відповідають різній кількості символів. 100 токенів англійської ≈ 75 слів. 100 токенів кирилиці ≈ 30-40 слів. `max_tokens` завжди в токенах, не в словах чи символах.

---

**Q: Що станеться якщо надіслати запит, що перевищує context window?**
A: API поверне помилку `400 Bad Request` з повідомленням про перевищення ліміту контексту. Модель не обрізає вхідні дані автоматично — це відповідальність розробника.

---

**Q: Навіщо `countTokens()` якщо можна просто надіслати запит?**
A: Дозволяє перевірити вміст у context window до реального запиту, уникаючи дорогого запиту що провалиться. Корисно при динамічному формуванні промптів (RAG, великі документи) — можна обрізати контент перед відправкою.

## Корисні числа напам'ять

```
1 токен ≈ 4 символи (англійська)
1 токен ≈ 0.75 слова (англійська)
1000 токенів ≈ 750 слів ≈ 1.5 сторінки A4

Українська: ~2-3x більше токенів ніж англійська
Context window Claude: 200,000 токенів ≈ 150,000 слів

Output дорожчий за input: ~3-5x
Cache read: ~10% від ціни звичайного input
```
